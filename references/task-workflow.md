# 共用开发检查

全局入口用于已授权的代码、配置、测试、构建与 Git 工作；日常 shoukou 的范围与原有成果保护规则不变。规则、检查器和项目资料分开维护：所有项目使用同一个 `scripts/task_guard.py`，项目只保存 `.codex/workflow.json`。

## 原生自动入口与轻量边界

**状态：底座试验中，未发布、未在其他真实项目启用。** 本节描述待验收实现，不是其他项目立即接入或发布开发中源码的依据。必须先完成底座独立反例验收，后续才安排原生信任和推广。

全局 `~/.codex/hooks.json` 将受支持的原生事件接入 `scripts/task_hooks.py`。非托管入口必须先经 Codex 的 Review hooks 审阅、信任；未信任会被跳过，不能报告已强制启用。安装器不编辑信任记录、不使用全局信任绕过参数、不改变沙盒或发布权限。

安装后的自动入口使用 `~/.codex/task-hooks/releases/<内容摘要>/` 中经过验收的固定运行文件，开发目录继续保留其他任务的修改。安装、验收本身也从明确选定的源码快照运行；报告、复制来源与运行文件逐项核对摘要。运行依赖在导入前由标准库校验，固定副本变化仍拒绝；升级通过新验收后生成新版本，不覆盖旧运行文件。原生审阅仍针对新入口定义执行。

- 普通咨询、已知只读命令不创建开发基线。第一次实际开发操作前自动记录一次；同聊天后续编辑沿用该记录，每次只检查小型状态、范围、受保护文件与必要的 Git 状态，不反复全量散列。
- 阶段结束才现场完整核对本轮；不会主动运行任何测试。普通开发阶段可以保留未提交草稿，记录尚待 Git 交付的项；实际收口才要求提交、分支和用户要求的合并、推送、同步或部署结果。
- 已有配置中的准确测试命令会自动转入共享 runner，使用其真实退出与回收回执。文案/样式改动默认拒绝无关整套测试；权限、配置、开发规则等改动不能因行数少而视为普通文案。语义判断和真实界面/业务验收仍按项目规范执行。
- 当前底座的完整访问模式已验证该 runner 路径；`workspace-write` 若拒绝写入 Git 内的任务回执，须保留真实失败并处理兼容性，不能偷偷放宽用户权限或把未记录的测试当作通过。其他项目接入前须核实实际权限模式。
- 原生 Bash 的操作后事件没有稳定的结构化退出码，自动入口会为可写命令追加每次独有的退出标记。标记缺失、命令失败或仍未结束时保留待办；无关成功不能消除它。
- 初次接入前已经有成果，不能用新基线证明那些成果已保存。沿用原任务时，执行者可用 `task_hooks.py --policy <安装回执中的策略路径> --state-root <同目录的 sessions> --bind-task <准确原ID> --repo <准确目录> --session <原生会话标识> --reason <具体关联依据>` 绑定已有记录。工具拒绝新建空任务、其他目录或无法说明现有差异的记录；不重置原基线。
- 暂停尊重用户指令；真实阻碍保留现场。相同遗漏连续未解决时以显式“部分完成、自动核对未通过”警告停止，避免无限续跑或为了通过而越权提交、删除。

新 Git 项目先只读核实实际输出位置与测试，使用准确的全局 `task_guard.py --repo <目录> init --output-root <目录>` 接入。首次配置可以补齐后再开始实际开发；不能把源码目录指定为输出根，也不能因缺配置直接跳过门禁。非 Git 目录不自动初始化或对外发布。

`scripts/validate_task_hooks.py` 使用桌面内置引擎和本地模拟模型，在隔离仓库及底座专属夹具执行反例，保留版本绑定的原始回执。仅该已审阅的临时测试进程使用原生的一次性 hook 信任绕过；真实全局安装不绕过信任。`install_task_hooks.py` 验证全部必需反例、底座实测和源码摘要后才写入全局配置；通过跨项目正控后可用 `--promote` 复用同一入口。安装使用不可变版本策略，合并保留其他已有 hooks。

本入口能拦截支持的 Codex 工具调用，但不是操作系统隔离。钩子本身缺失、平台错误/超时放行、特殊未覆盖工具、用户主动关闭钩子以及开发身份仍持有完整访问权限的情况，不能宣称无法绕过。管理员托管、主线和发布权限保护另行接入；不以后台异步脚本冒充同步门禁。

## 停用、恢复和卸载自动入口

管理入口是 `scripts/manage_task_hooks.py`，缺省只显示计划；带 `--apply` 才修改。`--home` 可指定安装目录，默认使用已设置的 `CODEX_HOME` 或 `~/.codex`。

```bash
python3 -B ~/.codex/skills/shoukou/scripts/manage_task_hooks.py status
python3 -B ~/.codex/skills/shoukou/scripts/manage_task_hooks.py disable --apply
python3 -B ~/.codex/skills/shoukou/scripts/manage_task_hooks.py enable --apply
python3 -B ~/.codex/skills/shoukou/scripts/manage_task_hooks.py uninstall --apply
python3 -B ~/.codex/skills/shoukou/scripts/manage_task_hooks.py recover --apply
```

- `disable` 暂时摘除本次安装回执确认的自动入口，保存原定义；`enable` 核对原程序、策略和验收摘要后逐项恢复，同时保留停用后新增的其他入口，绝不整文件覆盖。程序版本变化时须先重新验收安装。
- `uninstall` 卸载的是这套自动入口；共享的手动 shoukou、全局开发文字规则、项目适配、源码、业务数据、Git 任务历史及验收资料保持原样。它不是删除整个技能目录。其他任务仍使用的共用工具不能跟着删除；整套共享工具移除须另行核对所有引用和归属。
- 每次变更保留准确备份和操作记录。中断后 `recover` 只在配置仍精确等于变更前或变更后版本时恢复；并发改动、未知归属、符号链接或缺少回执时拒绝覆盖。卸载后的重新接入走验收安装，不靠恢复旧定义跳过版本检查。
- 停用与卸载不要求损坏的旧程序先通过版本检查；恢复运行必须通过。管理器不修改 Codex 原生信任记录，恢复后仍以原生审阅和实际事件为准。
- 原全局管理命令仍可使用：自动入口仅在调用这条命令时核对其已验收摘要，再同步调用固定管理实现。开发中的管理程序版本不符时只拒绝这条管理操作；可使用安装回执对应固定目录的 `manage_task_hooks.py`，普通项目检查不受开发目录变化影响。

## 修正后的只读诊断复核

旧入口已经记录失败、而只读诊断脚本需要修正时，使用本次安装固定目录中的 `manage_task_hooks.py review-diagnostic`。该动作须由当前已审阅入口同步执行，准确指定原项目、任务、会话和失败键；普通终端直接运行不会修改会话。默认只预览，`--apply` 才执行受限诊断并保存复核回执。

```bash
python3 -B '<安装回执 runtime_release>/manage_task_hooks.py' review-diagnostic \
  --repo '<准确原项目>' --task '<准确原任务>' --session '<当前原生会话>' \
  --failed '<原命令键>' --original '<原命令文本文件>' --corrected '<修正命令文本文件>' \
  --reason '<说明实际错误和修正>' --apply
```

- JSON 诊断只接受隔离 Python 查询的对象类型保护：在原文件遍历中，对刚由该文件解码的变量增加 `isinstance(..., dict)` 判断并跳过非对象。原读取、输出和范围必须保持相同；不能借此放行写入、业务命令、业务测试失败或无关成功。
- 另有独立的单进程查询复核：仅接受 `ps -o pid,ppid,pgid,etime,command -p <正整数>`（或明确的 `/bin/ps`），原命令与重查文本相同；重查实际固定为 `/bin/ps` 参数数组，不交给 shell。额外提供 `--native-source <原生日志路径和偏移原件>`、`--native-result <原事件原件>`；来源、偏移和原件摘要必须已由本次验收固定进安装策略，请求不能另选日志。原件必须与 Codex 原聊天日志、项目、工具 ID、完整包装命令及原退出标记相符，原结果只能是无错误的空表和退出 1。重查退出 1 必须仍为空表，退出 0 必须恰为所查编号的一行；原退出码均保留，表示“查询得到结果”，不计作测试通过。其他命令的失败不能套用退出 1。
- 进程查询只说明该数字编号当时或现在有无匹配，不证明是原测试的同一个进程，不授予停止进程、删除资源的权限。原生来源、回执、候选或策略变化会使旧复核失效；升级后须在原聊天重新复核，旧回执保留。
- 原失败集合和原始日志不删除。回执绑定准确失败事实、项目候选、任务、会话、策略及执行原件；任何一项变化，旧复核失效。每个跳过的文件、顶层类型和数量均明列，必须实际处理到有效对象；全部跳过不能当作成功，更不代表没有业务待办。
- 这是共用管理入口的诊断执行模式，复用短临时目录、目录身份、进程组和回收校验。十秒限时、每份日志最多 2 MiB，前后核对实际源码和配置输出；回执归入原会话 `diagnostic_attempts`，不新建空开发任务，不计作业务测试。失败尝试继续保留，未退出进程、未知状态及残留工作目录另行阻止结束，不被后一次成功掩盖。
- 成功的 Stop 回调可把安装记录更新为 `native-stop-audit-observed`，准确表示“这个入口已收到 Stop、审计通过并决定放行”。它不证明宿主已完成整轮、其他入口已通过，也不代替原生审阅或授予信任。

只读命令按引号和真实操作符区分。引号内正则、只读管道不再误作写入；限定的 Python 数据查询会自动转为隔离解释器执行，避免项目同名模块夹带写入。未知脚本、写文件、执行外部程序及动态执行不当作只读查询。正常写入仍使用原有成果保护和结束核对。

## 开工与连续处理

1. 先核实当前仓库、用户目标、项目要求和已有记录。读取项目配置；缺失时用工具 `init` 创建最小配置，测试命令、输出位置、远端和上线地址从现有文件与运行资料核实，未知项明确保留，不能猜。配置不放密钥。
2. 使用准确任务 ID 运行 `begin`，在首次修改前采集基线。已有任务复用同一 ID；先检查它的未完成事项，不能另开一个空记录掩盖旧尾巴。实现共用工具本身等先前已有的本任务差异，用 `--own-path` 精确纳入；原本存在的其他任务成果继续保护。
3. 必要项取自用户授权和项目要求，用 `--require` 固定；用 `--test` 选择本任务相关的测试，配置中的测试是可选目录，不是每次全部执行。已有必要项与所选测试不能缩减，可随同范围工作扩大。保存、合并、推送、本地同步、测试、部署与清理分别记录，不能为了通过检查删掉要求。工具记录位于 Git 共用目录，不提交进源码，也不是第二份资源台账。

```bash
python3 -B ~/.codex/skills/shoukou/scripts/task_guard.py --repo '<仓库绝对路径>' init --output-root '<已核实的项目相对输出目录>'
python3 -B ~/.codex/skills/shoukou/scripts/task_guard.py --repo '<仓库绝对路径>' begin --task '<准确ID>' --require commit --require cleanup --require branches --require tests --test '<相关测试名>'
python3 -B ~/.codex/skills/shoukou/scripts/task_guard.py --repo '<仓库绝对路径>' run --task '<准确ID>' --test '<项目已配置测试名>'
python3 -B ~/.codex/skills/shoukou/scripts/task_guard.py --repo '<仓库绝对路径>' check --task '<准确ID>' --phase final
```

`CODEX_HOME` 被明确设置时替换上述默认路径。参数及项目配置格式以工具 `--help` 为准。首次接入时，先自行核实测试与输出目录再开始任务；未配置输出根的项目不能获得清理完成。涉及另一个已登记工作目录时用 `add-worktree` 纳入，同任务开工前已存在的分支用 `--own-branch` 纳入；未改变的其他任务分支保持保护。底座用 `pnpm workflow` 转发到同一工具，不拷贝实现；其他仓库可直接调用全局脚本，无需安装新的依赖。

## 运行与回收

`run` 使用参数数组运行命令，提供本轮 `CODEX_TASK_TMP_ROOT`、`TMPDIR`、`TMP`、`TEMP`；项目原有 runner 的资源启停与校验继续有效。测试入口必须使用传入根或自己可靠的专用 workspace，不能覆盖成业务或共享位置。

运行根使用短系统临时路径，避免 macOS 的本地通信路径长度限制，不放进源码或业务目录。每条日志最多 2 MiB、每任务最多 64 次运行；日志截断会报告覆盖不足，运行次数达到上限则停止新执行并复核记录，不静默丢弃旧失败。

命令前后核对 Git 与配置输出根中的实际变化。命令退出失败、回收失败、仍在运行或发现名单外输出，均不能当作测试与清理完成。强制杀进程或断电不保证退出钩子执行；下次依据准确任务状态继续核对，只有确认本轮归属与身份的对象才能回收。来源不明的新增对象阻止“全部清理完成”，但不提供删除许可。

大文件、数据库、服务及外部资源复用原 runner 或 dev-artifacts 记录。必要证据与发布包保留用途、来源和后续复核条件；保留不能用来掩盖临时垃圾或未交付代码。限定扫描配置中的已知输出根，不遍历全盘，不把整个 `.runtime`、业务目录或缓存根认作可删对象。

已知失败命令留下的 `work`，先读取原始结果、核实资源确已停止，再用 `reclaim-run --task <ID> --run <准确运行ID> --evidence <原始证据绝对路径> --sha256 <摘要> --reason <具体依据>` 精确回收。工具验证原回执、进程组、目录身份和证据；只删该工作子目录，原失败结果与证据保持原样。回收不代表测试成功，仍须同一命令在对应候选上重跑通过；未知退出状态、活动进程或身份改变时保留现场。原生安全检查拒绝后不得换手段强删。

已完成运行的进程组编号以后可能被系统重复使用。复核先绑定该次运行的完整结束回执、目录身份和已回收工作目录；只有原记录与回执逐项相符，才认定该旧运行已经结束。缺少或变化的回执、未知进程状态、重新出现的工作目录继续检查，不凭编号推断归属。资源已结束不代表原失败变成功，也不授权停止当前占用同一编号的进程或删除目录。

测试回执写入遇到共用锁时最多等待 5 秒，超时保留中断，不解除锁或重置基线。若仅在工作目录回收后丢失最终回执，原记录和日志保持原样；只有原父进程、进程组均已退出，原目录身份可核实且工作目录已不存在，同一命令在当前候选重跑通过、回执有效时，终检才将旧中断列为已由新运行核对的历史记录。该判断不推断旧退出码，也不自动重跑或删除对象；条件不足仍保留待办。

## 交付与终检

阶段检查与最终检查区分执行，命令成功不等于整体任务完成。`--phase save` 核对本批必要的成果保存、保护和资源事实；它不代替 `final` 中的合并、推送、本地主目录、所选测试、部署和任务分支核验。工具现场发现基线后新增或改变的工作树、分支、输出和未保存修改；原主目录从 Git 登记核实，不能由发布副本替代。来源无法自动判定时，按检查输出中的对象与版本记录实际归属和原始证据；对象改变后旧决定失效。

本批共用终检可独立使用 `task_guard.py check --task <准确ID> --phase final`。日常终检脚本已支持 `lifecycle_task` 时，向 `verify_daily_closeout.py` 传入这个准确任务；脚本尚未接入该字段时，分别执行共用终检和原日常终检，不向旧脚本传入未知字段。两次结果均须通过，不能用漏填清单绕过开发基线。原有源码、重启依赖、真实远端和验收证据检查继续执行。

脚本返回非零时读实际未完成对象，继续可在原授权内完成的工作。原始失败不能用另一条无关成功命令覆盖。受阻记录只说明当前停止条件；恢复后重新现场检查，不能把“有阻碍记录”当作完成。检查不会合并、推送、切换、强删分支、覆盖暂存区或删除未知文件；这些操作仍走原有授权与安全核验。

技能文字不是命令拦截器。本地入口能拒绝经过它的不合格操作；未经过入口、未配置输出位置、外部服务与真实业务验收仍需其他证据。要禁止绕过合并或发布检查，应在对应托管平台和服务器配置受保护入口；本工具不改变这些权限。
