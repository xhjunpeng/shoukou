# 日常收口完成检查

日常路径结束前读取本页。仅核对本次请求、已有授权和项目要求中的必要项，不运行扩展目录审计，不把技能修改当作真实项目的收口或上线授权。

## 逐项核实

| 必要项 | 核对的事实 |
| --- | --- |
| 成果保存 | 本任务差异块、测试、数据库升级文件、必要依赖和发布脚本的保存版本；原目录没有本任务漏交成果。 |
| 验收 | 复用准确交付候选的原始结果；同范围可修复失败继续处理，未运行的检查明确写未运行。 |
| 合并、推送 | 真实远端、目标分支及包含本次成果的提交。缓存的 `origin/main`、提交标题或本地提交成功不能代替实时远端核对。 |
| 原主目录同步 | 用 Git 工作树登记找出实际主目录，核对分支、提交、相关修改、进行中的操作及使用者，遵守项目同步规则。其他活跃成果原样保留。 |
| 部署 | 包、发布源码和必要补丁能追溯到已保存提交及发布配置；实际运行版本和本次受影响操作得到验证。线上手工补丁不能留作唯一来源。 |
| 临时产物、分支 | 以实际删除或有依据的保留结果为准；运行、启动、重启、工作目录及回退引用不再依赖待删临时路径。分支仍走原有合入、占用和原生删除检查。 |

“来源不明”“目录有改动”“尚未检查”是需要继续核查的事实。先区分已交付但旧目录仍显示修改、本次漏交、其他任务仍在开发以及未知内容；不能把整份差异重复提交，也不能为完成同步而覆盖其他成果。

原目录同步受项目规则、其他任务或确实无法安全解决的冲突限制时，保留现场并停止该项；继续完成其他独立事项。说明受影响对象和版本、实际尝试、原始结果与继续条件。能在现有授权内取得的证据或完成的修复，继续执行；不要让用户重复授权同一步骤。

## 轻量只读检查器

对含 Git 同步、发布来源或临时运行依赖的日常收口，执行：

```bash
python3 -B scripts/verify_daily_closeout.py --input '<本次检查输入的绝对路径>' --json
```

执行者从用户请求和实际记录填写输入，不让用户手填字段。复用现有结果、发布清单和 runner 回收记录；小型输入按本次临时材料管理，不创建空资源台账或额外报告副本。纯咨询不运行检查器；未要求的项目不自动加入。

输入示意（替换为真实对象；以下路径和提交不是可直接使用的证据）：

```json
{
  "schema_version": 1,
  "task": "本次已选定的交付任务",
  "repo": "/absolute/release-checkout",
  "saved_commit": "已保存成果的完整提交号",
  "target_ref": "origin/main",
  "requirements": ["merge", "push", "local-main", "tests", "deploy", "cleanup"],
  "remote_target": {"remote": "origin", "ref": "refs/heads/main"},
  "local_main": {"path": "/absolute/original-main-checkout", "branch": "main"},
  "sources": [{"path": "/absolute/build-input/src/service.ts", "repo_path": "src/service.ts"}],
  "cleanup_has_services": true,
  "restart_dependencies": [{"script": "/absolute/start-service.sh", "paths": ["/absolute/task-temporary-root"]}],
  "evidence": {
    "tests": {"path": "/absolute/original-test-result.json", "sha256": "原始文件的SHA256"},
    "deploy": {"path": "/absolute/original-deployment-result.json", "sha256": "原始文件的SHA256"},
    "cleanup": {"path": "/absolute/original-runner-cleanup.json", "sha256": "原始文件的SHA256"}
  }
}
```

- `requirements` 必须覆盖本次所有必要项。合法名称为 `merge`、`push`、`local-main`、`sources`、`restart-dependencies`、`tests`、`deploy`、`cleanup`；不得为得到通过而移除用户要求的事项。始终核对 `saved_commit` 实际存在。
- `local-main` 核对明确指定、在同一仓库登记的实际主目录，不能用另一份干净发布副本替代。其他任务有未提交修改不一概判为漏交，也不产生提交、切换、覆盖或清理权限；原目录的本任务成果和其他成果保护仍须执行者逐段核查。
- `push` 实际查询 `remote_target`，核对实时远端与本地 `target_ref`，并自动核对目标包含 `saved_commit`，防止只验证旧版本已推送。可查询远端但目标分支不存在是待办；远端根本无法查询是查询错误，不能用缓存代替。不查询远端的本地模式不能宣称推送完成；`merge` 只证明已保存提交进入目标，不代替功能验收或其他代码的交付证明。
- `sources` 逐个比较登记源码与 `saved_commit` 内的对应文件；`deploy` 自动要求该检查。登记本次实际包或构建所用的源码和补丁，不能只列没有变化的样本。编译产物应核对构建输入与发布清单，再另外核对产物摘要和线上结果；不能把编译前后字节直接相等当作通用要求。一次输入对应一个仓库及保存提交；多来源构建为各来源分别执行 `sources` 检查，保留各次结果并核对覆盖整个发布清单，不能假填统一来源。检查器不会自动发现未登记来源。
- `cleanup` 必须说明 `cleanup_has_services`。有服务时自动要求重启依赖检查；没有服务时按实际记录填写 `false`，不启动服务或创建无意义的启动脚本。`restart_dependencies` 只读取明确登记的普通脚本文件，检查仍存在的临时绝对路径引用；路径已删除也会报告待办。相对路径、间接配置、动态依赖、运行进程及回退引用仍须按实际服务配置核对，脚本不会全盘搜索或执行命令。
- `evidence` 引用原有非空普通文件及实际摘要。脚本检查原件字节完整性，不接受仅填 `passed`，也不认证内容、授权、检查范围或外部事实。执行者须读原件，确认任务、候选版本、线上地址和结果适用；缺少事实继续取证，不写一份自述冒充成功结果。

## 待办与受阻

检查器复用 `closeout_progress.assess` 的逐对象处理：

| 输出状态 | 退出码 | 下一步 |
| --- | --- | --- |
| `complete` | 0 | 已登记检查无待办；仍须确认范围完整、授权有效及未自动验证的验收事实。全部必要项均完成才报告本次全部完成。 |
| `continue` | 3 | 按 `unfinished` 继续核查、修复或同步；不能仅报告部分完成就停止。 |
| `blocked` | 1 | 每个剩余对象都有对应版本的原始停点记录；读取并核实其真实影响，只报告部分完成和准确阻碍。 |
| 输入或查询错误 | 2 | 修正输入或核对实际查询失败，保留现场；不使用缓存或省略要求获得通过。 |

已有真实阻碍时，在输入 `stops` 中按输出对象键填写 `version`、`kind`、`attempt`、`result`、`release_condition` 和原始 `evidence:{path,sha256}`。沿用已有的暂停、任务保护、查询错误、范围边界、外部依赖或验收失败记录；版本使用检查器对应项的 `version`，不要猜。

可在原授权内修复的验收失败仍应继续。原件不存在、版本过期、证据摘要不符或只是“还没做”时不能形成有效停点。一个对象受阻不能覆盖另一个待办。脚本不认证停点的真实性，不授予强推、丢弃、越权提交、恢复暂停任务或删除目录的权限。

## 行为回归

`tests/test_daily_closeout.py` 使用自动回收的临时仓库和文件验证三个反例及修正后的结果：

1. 发布副本已更新且干净，但指定原主目录仍是旧提交：原目录同步未完成。
2. 发布输入或必要补丁与保存提交不同：发布源码交付未完成。
3. 临时路径已删，但重启脚本仍引用它：临时运行依赖未处理完。

还须验证其他任务的暂存、未提交和未跟踪文件在核对前后不变；原目录存在其他任务改动，不能诱发一起提交或覆盖。测试通过只证明这些行为，不能替代真实项目收口。
