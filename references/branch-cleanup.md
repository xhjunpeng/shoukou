# 分支收尾与新增分支复查

用于完整收口中的剩余分支；只读盘点、阶段交付及未知归属不获得清理权限。分支引用、目录和聊天分别核验，删除引用不等于回收目录或释放其容量。

## 旧目录仍有未提交状态

先查任务记录、应用关联及现有改动，确认任务归属、已结束、准确候选已验收且提交已进入主线、没有其他写入者或需要该分支引用的服务/任务。目录仍被历史聊天关联只阻塞目录回收；若分支本身有继续开发依赖，则继续保护。查不明的记录按实际查询失败报告，不让用户辨认分支，也不把“没有进程”当作任务已结束。

| 残留情况 | 处理 |
| --- | --- |
| 有未交付的独有内容 | 在已确认原任务范围内完成正常验收、提交和合并；不当作重复文件清理 |
| 未暂存或未跟踪文件与已交付版本相同 | 逐个绑定同路径、同模式、同内容的准确已验收提交；提交必须可从当前主线到达，再走下面的引用清理路径 |
| 文件是主线历史中的旧版本 | 查清主线后续修改及验收依据；符合上一行时原样保留旧文件，不覆盖当前主线，不将旧版本重新提交为新功能 |
| 暂存、冲突、删除/改名、特殊文件、子模块、隐藏索引或稀疏状态 | 不走重复文件例外；保留并走正常交付/专项核实 |
| 归属、结束状态、验收或依赖不明 | 保留对应对象并报告准确缺口，继续其他可完成项 |

**文件内容曾出现在 Git 历史里，只证明存在副本，不证明功能完整交付或获得删除授权。** 版本依据须来自原任务验收与交付记录；不要只搜到一个相同 blob 就宣布任务完成。

### 只清理分支名，原样保留目录

当前生效的全局“项目级收口的单窗口限定例外”及实际授权适用时，下列核查、原 HEAD 分离和引用删除可由统筹聊天直接执行，不要求唤醒原聊天或先移交目录。先确认来源仓库、注册工作树、任务结束与验收、无源码/Git 写入冲突以及不存在引用依赖；检查器不能替执行者认证这些事实。例外只覆盖本段的原样保留路径及另行核实的临时批次，不覆盖独有源码的跨目录修改或提交。

先读取快照（脚本只读，不创建 Git 恢复提交）：

```bash
python3 scripts/branch_cleanup.py --repo /absolute/project \
  --worktree /absolute/task-worktree --base main --observe
```

把返回的 `target` 原样放入目录外的最小检查输入，其他字段如下：

| 字段 | 必需内容 |
| --- | --- |
| `schema_version`、`mode`、`cleanup_authorized` | `1`、`full`、`true`；已有本轮准确清理授权 |
| `observed_at_unix`、`target` | 本次查询的时间和原始 `target`，不能手改头提交或文件指纹 |
| `task` | `ownership_confirmed`、`completed`、`accepted` 均为 `true`；`source` 指向实际任务归属、结束和验收依据 |
| `dependencies` | `checked: true`、`active_writers: []`、`requires_branch: false`；`source` 指向实际任务/进程及启动依赖核对 |
| `delivered_file_commits` | 恰好覆盖每个未暂存、未跟踪相对路径；值为该路径准确已验收版本的完整提交 ID。源码干净时填 `{}` |

```bash
python3 scripts/branch_cleanup.py --repo /absolute/project \
  --worktree /absolute/task-worktree --branch dev/task --base main \
  --evidence /absolute/outside-target/branch-evidence.json
```

源码干净和符合条件的重复未提交文件均使用上述检查，干净时 `delivered_file_commits` 为 `{}`。退出码 0 且 `branch_cleanup: passed` 后，统筹聊天可用 `git -C <准确工作树> switch --detach <原HEAD>` 分离到**原 HEAD**；用 `--observe` 复查 HEAD、`content_fingerprint`、暂存/未提交内容和目录均未变，再以 `git -C <已确认仓库> branch -d <准确分支>` 删除原引用。不先 `reset`、`clean`、`stash`、暂存/提交旧文件或改 HEAD 到恢复提交来制造“干净”；有独有成果时回到正常交付路径，并遵守跨目录开发边界。状态或写入者变化时停止并重查。

删除后，用同一证据和参数加 `--verify-preserved`，必须返回 `branch_cleanup: preserved`，证明原引用确实消失、目录仍在原 HEAD、非忽略源码和索引/未提交状态未变。该检查不验证忽略数据或所有运行依赖，继续执行原运行资料、服务与全目录复查。已有恢复引用/快照也要交代去向，不能仅把分支名称从列表隐藏就宣布整体完成。

脚本只核实可观察的 Git 和文件事实，不能认证调用者填写的授权、任务结束、验收或查询完整性；发现声明与原始记录不符时保持保护。它不删除目录，不改变聊天关联，也不放宽原生工作树回收门禁。检查输入按 storage-cleanup.md 的最小材料规则处理，结果直接写在聊天，不另导出报告。

## 遗留分支逐项取证

完整收口结束前，对每个仍存在的本地、远端任务引用分别填写最终台账的 `review`，包括原有和本轮新增引用。保留与清理都依据准确版本及实际记录；相同提交的几个分支仍可能对应不同未提交文件和任务。

1. **任务状态**：查最新用户约定及实际任务记录，区分 `completed`（用户已结束该任务，仍可能有验收阻碍）、`continuing`、`long-lived`、`paused`、`unknown`；记录来源。继续开发、明确长期保留或暂停约定确实要求保留该引用时可用 `agreed`，其余因阻碍保留用 `blocked`。尚未开展的核查进入 [执行待办](final-check.md#未完成工作与真实阻碍)，不只填“未知”结束。
2. **成果去向**：记录准确头、验收结论、逐目录未提交成果及对应去向。检查器另实时报告头提交是否为主线祖先；这不包含未提交成果，也不替代 squash/rebase 的准确 PR 证明。旧来源已接续到候选时继续查候选是否真正交付，不能用“已复制”“已备份”代替。
3. **分支本身的依赖**：核实继续开发、写入者、未完成 PR、启动及服务配置是否确实需要这个引用。目录或服务仍在使用，不等于需要保留分支名；目录缺失、聊天不能移交、原生回收入口不可用，只能单独阻塞目录，继续判断引用。
4. **阻碍处理**：填写实际查询/失败来源、已查明事实、下一项具体操作、执行位置和可检查的解除条件。验收失败先定位到准确候选与失败项；原授权内的正常验收和必要修复连续完成。公共工具或其他项目修改、继续开发任务、服务迁移等越界事项单列范围，不冒充本项目必须停止全部收口。

未合并、未提交或验收失败是保护现状的理由，也是继续核对交付路径的起点。能在本轮完成的步骤继续做；确实受阻才留下具体处理记录。同一事实已核清时复用，不反复追问，也不反复仅列“未合并/未提交”。所有阻碍都不构成强删许可。

在每个 `retained` 的 local/remote 对象内加入：

```json
{
  "review": {
    "head": "与该引用本次核验一致的完整提交ID",
    "task": {"state": "completed", "source": "真实任务及用户约定来源"},
    "delivery": {
      "accepted": false,
      "uncommitted": "pending",
      "source": "准确候选验收结果、逐目录文件清单及成果去向来源"
    },
    "dependency": {"required": false, "source": "对该分支引用的任务及运行依赖核查来源"},
    "blocker": {
      "kind": "acceptance",
      "source": "本次实际失败项或查询错误的原始来源",
      "finding": "已核查的失败事实及其影响",
      "next_action": "下一项具体操作；越界时列明所需范围",
      "execution_location": "准确聊天、目录或工具入口",
      "release_condition": "什么实际结果出现后可继续交付或清理"
    }
  }
}
```

- `delivery.accepted` 取 `true`、`false` 或 `null`（未核实）；`uncommitted` 取 `none`、`pending`、`delivered-copy` 或 `unknown`。`delivered-copy` 需真实同路径已交付版本及验收证据，走上文重复内容检查；不是“在另一个目录看到了副本”。本地引用声称 `none` 时，其已检出工作树必须确实无非忽略改动。
- `dependency.required` 取 `true`、`false` 或 `null`；`true` 表示确需保留该引用，须有真实依赖来源。未知仍保护；不能写成 `agreed`。任务明确继续/长期保留且该引用确需保留时才使用 `agreed`。
- `blocked` 必须含完整 `blocker`；`kind` 为 `acceptance`、`delivery`、`branch-dependency`、`ownership`、`git-state` 或 `tool`。`tool`/`git-state` 必须指向阻塞引用核验或操作本身的真实错误，目录回收入口不可用不能换标签绕过。验收已通过、准确头已在主线、无未交付文件且无引用依赖时，不能再以验收/交付/依赖未完成结束调查。
- `agreed` 无需 `blocker`。所有来源均指已有真实记录或最小必要原始证据，不另制作报告或复制整套材料；来源不能只回指本条保留理由。

检查器拒绝缺少记录、版本不符、未知或结束任务伪装成约定保留、目录问题充当分支阻碍、与可观察 Git 状态矛盾的声明。它只检查结构和可观察事实，不能认证来源内容、授权或依赖判断；执行者仍须读取原始记录，最终在聊天逐条交代遗留分支及具体解除条件。

## 收口期间新增的分支

项目级完整收口在首次 Git/清理动作前运行 `verify_closeout.py --capture-branches`，保存原始本地及真实远端头清单与 SHA-256，写入最终台账的 `branch_inventory`。不通过重新采集“操作前”清单隐藏新增或遗漏；缺少初始清单时该项为未评估，整体只能部分完成。

结束时对比原始清单、候选台账和实时引用；原始分支即使已删除也必须逐个交代。新增分支单列准确头、来源与状态：已结束且有准确交付和清理授权的任务可按正常路径处理；继续开发或政策长期保留的分支保护；未知对象保留为受阻。新增不等于可删，也不自动扩大原有任务范围。

最终检查会在耗时的数据/服务复核后再次读取本地和真实远端引用。期间出现新增、移动或删除时返回受阻，重新核对变化对象和新鲜台账；并发开发持续变化时如实报告未完成，不循环强制清理或要求其他聊天停工。最终分开报告本轮已收口分支、后续新增任务、保护/受阻对象，以及目录、聊天和运行资料的去留。
